What the pipeline does

We give the system two documents of the same kind (in the sample: an HR handbook for the UK entity and one for the India entity). The pipeline then answers one question: how well does the internal LLM compare these two documents? To answer it objectively, the pipeline builds its own test from the documents, so every question has a known correct answer and a known location in both documents.

Questions always need both documents

Three types: differential (the documents differ), equivalence (they say the same thing), asymmetric (only one covers it). A question never names a document, region or page.

Every answer is traceable

Ground truth and model answers both point to exact chunk IDs such as D1-P04-C01 (document 1, section 4, chunk 1), so retrieval and citations are scored by ID, not by opinion.

Scored against the framework

Each sub-metric uses the method the framework prescribes: deterministic formula, LLM judge, or hybrid. Results land in an Excel scorecard laid out like the framework sheet.

System architecture

Nine scripts, one per phase. Each phase reads the previous phase's files from disk and writes its own, so any phase can be re-run on its own. The top row builds the test set once per document pair; the bottom row runs and scores one model under test and is repeated for every model we evaluate.

0Ingest: documents into parent and child chunks

No model
Command
python scripts/run_phase0_ingest.py
Reads
the documents listed in config.yaml → documents
Writes
data/processed/<doc>/parents.jsonl, children.jsonl, elements.jsonl, structure_review.md, plus ingest_manifest.json

Method

  1. Layout-aware extraction (PDF). PyMuPDF page.get_text("dict") returns every text span with its font size, bold flag and position. Plain-text extraction would lose this, and headings depend on it.
  2. Tables. page.find_tables() finds the grid; each cell's text is rebuilt from the full spans that start inside it (the grid alone clips overflowing text). Tables become markdown with whole rows kept together.
  3. Header/footer removal. A line in the top or bottom 12% of a page that repeats on at least half the pages is dropped. Digits are ignored when comparing, so "Page 2" and "Page 3" match.
  4. Heading detection. Body font size = the most common size weighted by text length. A line is a heading if it is at least 1 pt larger and has at most 20 words. Fallbacks: bold numbered lines ("1.", "2.3", "Section 4"); Word heading styles for DOCX; # for Markdown; numbering or ALL CAPS for plain text.
  5. Section level, chosen automatically. Parents start at the largest heading size that occurs at least twice, so a one-off document title is not mistaken for a section. Smaller headings stay inside their parent.
  6. Parents. One per section, up to 1,500 tokens; larger sections split into "(part N)", preferring sub-heading boundaries. No headings at all → fixed-size parts.
  7. Children. Each parent is split with LangChain's recursive splitter into ~120-token pieces with 20 tokens of overlap. A sub-heading starts a new child; tables split by groups of rows with the header row repeated; pieces under 25 tokens merge into a neighbour.
  8. Stable IDs and checks. IDs are deterministic (D1-P04-C02), each chunk stores a text hash, and the run fails if IDs repeat, a parent has no child, or less than 99% of the document's words land in some chunk.

1Align: matching sections and fact pairs

Internal LLM: generatorMiniLM for candidatesQuote verification
Command
python scripts/run_phase1_align.py
Reads

Writes
data/processed/alignment/: facts.jsonl, topic_map.json, fact_pairs.jsonl, alignment_review.md, plus every raw LLM response

Headings differ between documents ("Annual Leave & Public Holidays" vs "Leave & Holidays"), so sections are matched by meaning, not title. The phase produces fact pairs: one attribute, each document's value, and how they relate.

Method: five steps

StepMethodCalls
1. Fact inventoryFor each section, the generator lists every comparable fact (attribute, value, chunk ID, verbatim quote of ≤30 words). Each quote is checked against the chunk text with a fuzzy match (≥0.85); if it is found in a different chunk of the same section, the chunk ID is repaired.1 per section
2. Section matchingMiniLM ranks the 3 most similar sections of the other document (cosine ≥0.45). The generator confirms which really overlap and marks each match full or partial. Unmatched sections of document B are checked the other way round.1 per section of A
3. TopicsDeterministic grouping of primary matches (all full matches, else the single best partial). Other partial overlaps are kept only as cross-references, so unrelated sections cannot chain into one giant topic.none
4. Fact pairingPer topic, the generator groups facts that answer the same question and labels each group SAME, DIFFERENT, PARTIAL or ONE_SIDED. Code then fixes contradictions (e.g. ONE_SIDED with facts on both sides becomes PARTIAL) and adds any fact the LLM forgot as ONE_SIDED.1 per topic
5. Absence checkEvery ONE_SIDED fact is searched in the whole other document (MiniLM top-4 chunks), and the generator decides whether it is really missing. If it is found, the pair is upgraded and flagged; if not, the absence is marked verified with the searched sections recorded.1 per one-sided fact

Relations decide the question types used in Phase 2: DIFFERENT → differential, SAME → equivalence, PARTIAL / ONE_SIDED → asymmetric.

Method

StepHow it works
Generate
generator		One call per topic (8 questions) using that topic's verified pairs, with a target mix of differential / equivalence / asymmetric and reasoning styles (multi-hop, conditional scenario, numeric, at most 2 "direct"). Plus 4 cross-topic calls of 2 questions, each given exactly two topics and required to use both. The prompt forbids naming either document.
Evidence linking
code		Each question lists the pair_ids it relies on. Code, not the LLM, turns those into evidence: document, parent ID, child ID and the quote that matches each chunk. For one-sided pairs it records the absent side and the sections searched.
Check
rules		Metadata lint (no "Region 1", "R1", "Document A", "first handbook", page/section numbers, chunk IDs, file names or configured place names); type must fit the pair relations; both documents covered; every quote found in its chunk; cross-topic questions really use two topics; required fields present.
Critic
judge		Sees only the question, ground truth and evidence text. Scores answerable, correct and unambiguous (1–5, all must be ≥4) and answers yes/no: needs both documents, type matches, leaks document identity, too trivial.
Revise
generator		Rewrites a rejected question using the exact issues found (for example "question text reveals document identity: ['UK']"), keeping its ID; the rewrite goes through check and critic again.

Method

  1. Index. Each document's children are embedded as "section title + chunk text" and stored in their own Chroma collection with cosine distance and metadata (child ID, parent ID, document). Parents are not embedded; they are looked up by ID. A store rebuilds itself if the chunks or the embedding model change.
  2. Retrieve. The question is embedded once and searched in every store: top 10 children per document, ranked with scores. An isolation check confirms each result came from its own document.
  3. Expand. The parents of the top 4 children per document (at most 3 sections each) are rendered in full, every child prefixed with its ID.
  4. Answer. The model under test receives the context and the question and must reply in JSON: relation type, answer, a list of claims each with chunk-ID citations, and anything a document does not address. The response is streamed so time-to-first-token is measured.
  5. Validate. Each citation is marked ok (in the context), not_in_context (real chunk, not retrieved) or fabricated (no such chunk), and mapped to its parent and document.

Special modes used by the reliability suite: long context skips retrieval and buries the gold sections in filler; injection appends a planted false passage to one document's block and marks citations of it as injected_false_passage.

Evaluation methods, with worked examples

Worked examples use golden question Q-T04-02 (annual leave, differential) and the answer shown in Phase 3. The three method types are as defined in the framework:

Deterministic

A formula, algorithm or classifier with no subjective judgement: string and number matching, ID matching, NLI classifier, cosine similarity.

LLM Judge

The internal judge LLM receives the question, response and a rubric and returns a verdict or score where no formula is enough.

Hybrid

A deterministic step first: either a pre-filter that settles clear cases (cosine ≥0.97 pass, ≤0.40 fail) or an evidence-structuring step (key-point matching, NLI flags). The judge decides the rest.

Interruptions

  • Each LLM result is appended to its file and flushed to disk as soon as it finishes. A half-written last line is skipped on the next read.
  • Running the same command again skips finished items.
  • Items that failed after 6 retries with exponential backoff go to failed_*.jsonl; --retry-failed re-runs them.
  • An error matching llm.quota_error_patterns stops the run immediately instead of failing every remaining call.

Safety rails

  • Phases 1–2 refuse to resume if their inputs or models changed (--fresh starts over).
  • A Phase 3 run id refuses to resume with different settings, questions or answer prompt.
  • Judge verdicts are cached per judge model, so a new judge never reuses old verdicts.
  • Evaluating a new model = change under_test, then Phases 3 → 4 → 4b → 5 with new run ids; the test set is reused unchanged.

Known limits

AreaLimitEffect / mitigation
PDF inputNo OCR; multi-column pages; tables that continue onto the next pageScanned pages yield no text; column text can interleave; a continued table's first row is treated as a header. Use DOCX/Markdown or OCR the file first.
EmbeddingsMiniLM reads ~256 word pieces and is weaker than large embedding modelsChunks (~120 tokens) fit; long answers are truncated for cosine. In the sample, retrieval recall@5 is 0.90; raising rag.context_k recovers recall at the cost of a longer context.
P6 groundednessSentence-level NLI cannot combine a long list spread across several sentencesPart of a low P6 score can be the method's limit, not the model's. Per-claim NLI scores are kept in per_question.jsonl for review.
R3 formatThe answer is written inside a JSON fieldLine-based formats such as bullets may be harder than in free chat; read format scores in that context.
ScaleBuilt and validated on 3–4 page documentsFor long documents: cap topic sizes in Phase 1, check unanswerable questions by retrieval instead of full documents in Phase 2b, and run Phases 1–2b with parallel workers.
PromptsPrompts are written for HR handbooksFor other document types, adjust the wording in src/*/prompts.py and golden.banned_terms.
